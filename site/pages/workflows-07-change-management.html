Workflow 07 — Change Management

When a change request arrives

  • Capture a durable Request when provenance/change history matters.
  • Analyze affected canonical entities and incoming/outgoing relations.
  • Perform potential impact analysis.
  • Create/update canonical Feature/Requirement/Rule/Screen/Flow/API/DB/Test docs.
  • Record a Decision when the change requires a meaningful product/architecture choice.
  • Update Blueprint/Traceability/Changelog as needed.
  • Promote the Request to the durable target entities.
  • Run validation and the Ready gate.
  • Create/review/approve a WorkPlan.
  • Materialize implementation Tasks only from the approved non-stale plan.
  • After implementation, reconcile docs/tests and run the Done gate.

Do not

  • Jump from request text directly to code.
  • Treat the Request note as the final requirement.
  • Create implementation Tasks before documentation is Ready.
  • Approve a WorkPlan after documentation changed.
  • Fix a gate failure by weakening policy without review.
  • Put new business rules only inside Task notes.
