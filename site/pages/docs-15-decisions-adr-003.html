Fractional-Index Positions for List and Card Ordering

docs/15-decisions/ADR-003.md

Architecture / Product Decision Record

Context

Drag-and-drop reordering of Lists (on a Board) and Cards (within a List) must be fast and must not require rewriting every sibling row on each move, since that would be both slow and a concurrency hazard under frequent reordering.

Decision

Store position as a double precision fractional-index value per DB-LIST/DB-CARD. Inserting/moving an item between two neighbors sets its position to the midpoint of theirs. When the gap between neighbors becomes too small to split further (float precision floor), the server rebalances all sibling positions to evenly spaced integers as part of that same request (BR-LIST-002).

Options Considered

  • Fractional index (chosen) — O(1) write per move in the common case.
  • Integer position with full renumbering on every move — simple but O(n) writes per move, and a concurrency hazard (every sibling row changes, increasing conflict surface).
  • Linked-list (prev/next pointers) — O(1) per move but more complex queries to materialize ordered lists, and harder to reason about under concurrent writes.

Rationale

Fractional indexing is a well-established pattern (used by Trello, Figma, and others) that keeps the common case cheap while the rare rebalance keeps precision from degrading indefinitely.

Consequences

API-LIST-REORDER and API-CARD-MOVE share this mechanism (BR-LIST-002). Both are documented to potentially touch more than one row on the rare rebalance path, which API consumers should not assume away.

Risks

Rebalancing touches every sibling row in that board/list, which is a larger write than normal; acceptable given rebalances are rare and lists/boards are bounded in size at MVP scale.

Affected Entities

DB-LIST, DB-CARD, API-LIST-REORDER, API-CARD-MOVE.

Status

Accepted

Supersedes / Superseded By
