JWT Access Token + httpOnly Refresh Token Cookie for Sessions

docs/15-decisions/ADR-002.md

Architecture / Product Decision Record

Context

The system needs a session mechanism that is secure against XSS token theft, works for a React SPA calling a separate Node.js API, and supports silent re-authentication without forcing frequent logins.

Decision

Issue a short-lived JWT access token (returned in the login/register response body, held in memory by the SPA, sent as Authorization: Bearer) plus a long-lived opaque refresh token stored server-side (hashed) and delivered to the browser only as an httpOnly, Secure, SameSite=Strict cookie.

Options Considered

  • JWT access + httpOnly refresh cookie (chosen) — access token not persisted to storage (mitigates XSS token exfiltration), refresh token inaccessible to JavaScript.
  • JWT in localStorage — simpler but vulnerable to theft via any XSS.
  • Server-side session only (opaque cookie, no JWT) — simpler but couples every request to a session store lookup; JWT lets most requests avoid that round trip.

Rationale

Balances statelessness (fast, no lookup needed) for the access token with revocability (the refresh token row in DB-REFRESH-TOKEN can be revoked server-side on logout) for the long-lived credential.

Consequences

API-AUTH-LOGIN/API-AUTH-REGISTER set the refresh cookie; API-AUTH-LOGOUT revokes it; DB-REFRESH-TOKEN exists specifically for this. See docs/10-security/authentication.md and NFR-SEC-001 for the concrete expiry values.

Risks

Access-token expiry must be short enough to limit exposure if somehow leaked, but not so short that it causes excessive silent-refresh traffic — tuned in NFR-SEC-001.

Affected Entities

MOD-AUTH, DB-USER, DB-REFRESH-TOKEN, all authenticated APIs.

Status

Accepted
