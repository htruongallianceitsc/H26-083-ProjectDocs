AI Agent Rules — v5.3

  • Documentation first; do not produce implementation code unless implementation is explicitly requested and allowed.
  • Resolve documentation depth before expanding a Feature. Do not assume Full detail is always better.
  • lightweight is valid for suitable mock/POC/prototype work; keep the same canonical Feature identity when later promoted.
  • Never create Requirement/Test/API/Screen/DB entities merely to satisfy folder structure or a numeric gate. Create them when confirmed knowledge and the selected spec profile require them.
  • Use spec:recommend when maturity/risk is unclear. Respect risk escalation policy and explain when the requested level is below recommendation.
  • Do not turn assumptions into facts; record unresolved blockers as Open Questions.
  • Capture durable Requests when change provenance matters before mutating canonical scope.
  • A Request is intake/provenance, never the final Feature/Requirement/API/Screen/DB specification.
  • Before significant edits, run typed graph impact analysis; never infer impact from filename similarity alone.
  • Review HIGH impact entities before finalizing a change.
  • Do not duplicate canonical content into Tasks or WorkPlans.
  • Every new domain entity needs stable code, type, owner/status and meaningful relations.
  • Keep PROJECT_BLUEPRINT.md and traceability aligned after documentation phases, including Feature spec level/maturity.
  • Reconcile important Feature docs to activate dependency freshness tracking.
  • Never clear STALE by refreshing hashes without reviewing changed dependencies.
  • Before implementation planning, run spec compliance, validation, freshness and the mode-aware Ready gate.
  • WorkPlans live outside product truth and require explicit authoring/review. WorkPlans snapshot effective spec level and maturity.
  • Never approve a WorkPlan after STALE_CONTEXT; re-read/re-author against current docs.
  • Materialize Tasks only from an approved, non-stale WorkPlan unless an explicit project exception exists.
  • Tasks point back to canonical Feature/Requirement/Screen/API/DB/Test/Request context and do not invent product behaviour.
  • After implementation, reconcile canonical docs/tests before expecting Done to pass.
  • Use spec:promote before increasing depth. Read its gap report, add only justified canonical docs, then apply the new level.
  • Capture meaningful semantic batches as ChangeSets; create Baselines at UAT/release/migration boundaries.
  • Do not rewrite accepted Decisions; supersede them with a newer Decision.
  • State clearly what is confirmed requirement versus suggested design.
