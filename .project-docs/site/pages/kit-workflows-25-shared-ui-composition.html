Workflow 25 — Shared UI Composition

Goal

Turn repeated Screen chrome into canonical reusable UI while preserving Screen-owned behaviour.

Steps

  • Build/review current Screen wireframes.
  • Identify repeated regions/components.
  • Create/review ui-component documents with stable slots.
  • Create/review a screen-shell when the same placement recurs.
  • Add screen.related.screen_shells and optional direct screen.related.ui_components.
  • Add Screen Shared UI Overrides only for declared slots.
  • Keep User/Lifecycle/System/API actions on the Screen.
  • Run registry/docs validation and impact analysis.
  • Rebuild wireframes.
  • Verify shared ownership badges, active tab/header differences, navigation destinations and stale-dependency behaviour.

Exit criteria

  • No unnecessary duplicated Header/Bottom Navigation structure across consuming Screens.
  • Every shared placement resolves to a canonical ui-component.
  • Shell/component relations support Component → Shell → Screen impact traversal.
  • Screen overrides use declared slots only.
  • Shared changes make dependent wireframe projections stale until rebuild.
