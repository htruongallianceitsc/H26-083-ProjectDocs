# Architecture / Product Decision Record

## Context
Multiple users commonly view the same board at once. Changes made by one user (card moves, list reorders, label/member changes, comments) must appear for everyone else viewing that board without a manual refresh or aggressive polling.

## Decision
Expose a WebSocket endpoint (`/ws/boards/{boardId}`) that every write API broadcasts a typed event to after a successful commit (`card.moved`, `card.created`, `card.archived`, `list.reordered`, `label.assigned`, `comment.created`, etc.), scoped to clients currently subscribed to that board's channel.

## Options Considered
- **WebSocket (chosen)** — low-latency, bidirectional-capable channel well suited to a board that many users may actively edit.
- **Server-Sent Events (SSE)** — simpler (one-directional), would have worked for broadcast-only needs, but WebSocket was chosen for future flexibility (e.g. typing indicators, presence) without a protocol change.
- **Polling** — simplest to implement but adds latency and unnecessary load proportional to the number of open boards.

## Rationale
The product's core value proposition (trustworthy realtime collaboration on a shared board) depends on sub-second propagation of changes; polling cannot meet that cheaply at scale, and WebSocket leaves room to add presence/typing-indicator features later without re-architecting.

## Consequences
Every mutating API in `docs/07-api/` documents its WebSocket broadcast under "Performance / Rate Limit" or "External Dependencies". See `docs/09-architecture/realtime-architecture.md` for the connection/subscription model.

## Risks
WebSocket connections require sticky routing or a pub/sub fan-out layer if the API is horizontally scaled across multiple instances — noted in `docs/09-architecture/realtime-architecture.md` as an operational consideration, not yet a blocking concern at MVP scale.

## Affected Entities
`MOD-BOARD`, `MOD-LIST`, `MOD-CARD`, `MOD-LABEL`, `MOD-MEMBER`, `MOD-COMMENT` (every write API that broadcasts an event).
