# Architecture / Product Decision Record

## Context
KanbanFlow is an authenticated, highly interactive application (drag-and-drop, realtime updates) with no public/SEO-relevant pages. The team must choose a frontend rendering strategy.

## Decision
Build the frontend as a client-rendered React single-page application (SPA), served as static assets, communicating with the Node.js backend purely via REST + WebSocket. No server-side rendering (SSR) framework in v1.

## Options Considered
- **Client-rendered SPA (chosen)** — simplest deployment (static hosting + CDN), no SEO benefit to lose since the app is entirely behind login.
- **SSR framework (e.g. Next.js)** — would add build/deploy complexity and a Node rendering server with no corresponding product benefit for a behind-login app.

## Rationale
Every screen in this product (`docs/05-screens/`) requires authentication; there is no public marketing or indexable content that would benefit from SSR. A plain SPA keeps the frontend deployment simple (static hosting) and decoupled from the API's deployment lifecycle.

## Consequences
`docs/09-architecture/frontend-architecture.md` documents the SPA's routing, state, and data-fetching approach per `standards/stacks/web/reactjs/*`. Static hosting/CDN strategy is noted in `docs/12-devops/environments.md`.

## Risks
If a future requirement adds public/SEO-relevant pages (e.g. a marketing site, public roadmap), those would be built separately rather than retrofitted into this SPA.

## Affected Entities
All `SCR-*` screens; `docs/09-architecture/frontend-architecture.md`.
